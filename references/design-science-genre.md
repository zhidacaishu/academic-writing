这类论文的核心评价依据是“问题 → 设计 → 评估”三者之间的闭合关系。审稿人通常关注以下三个问题：

1. 这个问题是否确实存在且具有重要性，还是仅由作者设定而缺乏实际或文献依据？
2. 你的设计是针对这个问题的，还是只是换了个更复杂的模型？
3. 评估证明的是你声称的那件事吗？

下面所有规范都服务于让这三个问题有明确答案。

## 一、挑战、设计、贡献与评价：建立可追溯闭环

这类论文应使读者能够从问题、挑战或解法目标追踪到设计理由、贡献声称和评价证据。若研究问题能够自然分解为若干相对独立的挑战，**最好**采用一致的编号、顺序和核心术语，形成接近一一对应的结构；这能降低读者的核对成本，但不是有效性的必要条件。

真实关系可能是一对一、一对多、多对一或交叉作用。不得为了凑齐相同数量的条目而人为拆分挑战、重复贡献，或设计没有实质意义的消融实验。存在交叉关系时，使用映射表或显式回指说明：

```
问题、挑战或解法目标
        ↓ 一对一、一对多、多对一或交叉作用
设计原则、关键机制与实现
        ↓
贡献声称
        ↓
与声称类型相匹配的评价证据
```

最低闭环要求：

- 每项核心挑战或解法目标至少由一个设计元素回应。
- 每个关键且非显然的设计元素都有问题依据或知识依据；普通实现细节不必单列为贡献。
- 一项贡献可以概括多个相互配合的设计元素，一个设计元素也可以支持多项贡献。
- 每项核心贡献和强声称都有相应证据；评价覆盖的是**声称**，不是机械覆盖所有组件。
- 只有当设计可以合理拆分，且论文声称某组件具有增量作用时，才要求消融。不可合理移除的整体设计、形式性质、可解释性、效率或部署成效，应分别采用定理或证明、仿真、敏感性分析、案例或用户研究、运行时间或复杂度分析、现场评价等合适证据。
- 若不同层级不是一一对应，列出“挑战或目标—设计—贡献声称—评价证据—适用边界”映射表。

Peffers et al. (2007) 的 DSRM 要求问题识别、解法目标、设计、展示与评价形成连贯过程，但不要求各阶段产生相同数量的条目。ISR 2024 的设计研究编辑文也明确反对将不同 artifact 强行装入单一模板，并强调评价方式应匹配 artifact 与知识声称。[Peffers et al. (2007)](https://doi.org/10.2753/MIS0742-1222240302)；[Abbasi et al. (2024)](https://pubsonline.informs.org/doi/full/10.1287/isre.2024.editorial.v35.n2)。

常见的挑战类型（供对照，不是模板）：

- 数据层面：稀疏、高维、非平稳、异质
- 行为层面：多面性与并发、动态交互、外部事件影响
- 方法层面：既有模型的假设过强、参数量随组合爆炸、隐变量不可识别
- 可用性层面：黑箱模型无法支撑管理决策

### 挑战怎么写

- 一个挑战一段，段首直接命名，段尾用一句收束成可操作的技术问题（"因此，挑战在于如何……"）。
- 挑战必须能够转化为可由 artifact 回应的解法目标；它可以是方法、信息表征、决策、组织或社会技术层面的困难。单纯场景描述必须进一步说明其为何构成设计要求，以及既有解法为何不能满足。例如，“电商数据规模大”本身不是充分挑战；“枚举所有行为组合会导致参数量指数爆炸，因而无法在目标规模下建模并发行为”才形成可评价的设计要求。
- 证据应定位到具体方法族：说明哪一类方法因何种假设而无法处理该问题。仅写“现有研究存在不足”不能构成有效论证。
- 将挑战提炼为 2–4 个通常便于沟通，但这只是启发式，不是硬约束。数量由问题结构决定，不得为维持形式对应而合并不同问题或拆分同一问题。

## 二、Justificatory knowledge 与理论：先检索相关性，再决定是否使用

当任务涉及理论定位、设计依据或贡献层级时，理论适配检查和有针对性的文献检索必须进行，但不得把具名 kernel theory 当作所有设计科学论文的通行证。先检查原稿的理论主张，再检索并核实与研究问题、作用机制、构念、artifact 类型和情境真正相关的解释性理论、既有设计知识、技术知识与领域证据。润色模式不得擅自新增理论标签或引用。

只有理论通过以下适配检查时，才把它写成设计依据：

1. 理论构念或分析单位能与研究中的变量、行为者、过程或设计对象建立明确映射。
2. 理论机制能解释为什么某项设计可能达到目标，而不只是与研究主题使用了相似词汇。
3. 理论的适用边界与当前情境不冲突；存在差异时能够说明如何调整。
4. 理论至少产生一项可观察的设计含义，例如需求、变量选择、结构、约束、目标函数、交互机制或评价命题。

若理论只提供背景语言，不能产生设计含义，不得称其为 kernel theory 或 theory-guided design。

### 何时理论是必须的

以下情况必须提供相关理论或明确的理论框架，并展示“理论命题 → 设计含义 → 实现 → 评价”的链条：

- 论文明确声称 artifact 由某项理论指导。
- 论文声称检验、扩展或形成理论贡献。
- 论文把成果定位为较成熟的 design theory。
- 核心贡献依赖对用户、组织或社会技术机制的解释，而不只是证明 artifact 达到某项性能标准。

### 何时理论最好有

- 模型变量意在代表既有理论构念。
- 研究希望解释设计为何有效，而不只是报告是否有效。
- 研究希望把单个 artifact 的经验抽象为可跨情境迁移的设计原则。
- 目标期刊和相关研究传统重视较高层次的理论抽象。

### 何时可以不用具名理论

若主要贡献是新 artifact、算法、表征、方法或早期 invention，且经过有针对性的文献检索后没有理论能够通过上述适配检查，可以不写具名 kernel theory。不得为了满足体裁预期而贴上无关理论标签。

没有具名理论不等于没有知识基础。稿件仍须说明真实问题与利益相关者需求、既有 artifact 和设计知识、领域事实与技术或制度约束、关键设计理由及备选方案，并提供与声称相匹配的严谨评价。证据允许时可以提炼初步设计原则及适用边界，但不得声称已经形成或扩展了理论。若目标期刊明显要求更强的理论贡献，应提示定位或选刊风险，不能补写不相关理论。

Gregor and Jones (2007) 的完整 IS design theory 包含 justificatory knowledge；这套要求适用于声称 design theory 的成果，不等于每篇 artifact 论文都必须达到该层级。Gregor and Hevner (2013) 区分 artifact、初步设计知识与成熟设计理论；ISR 2024 编辑文进一步承认没有 formal theory-guided design 的 emergent design insights，并提醒不要强套 artifact 模板。[Gregor and Jones (2007)](https://doi.org/10.17705/1jais.00129)；[Gregor and Hevner (2013)](https://doi.org/10.25300/MISQ/2013/37.2.01)；[Abbasi et al. (2024)](https://pubsonline.informs.org/doi/full/10.1287/isre.2024.editorial.v35.n2)。

## 三、引言里的示例图

本领域的方法论文通常在引言或紧随其后放一张具体示例图：例如一条真实的用户旅程、一段真实的行为序列，把可见的行为与不可见的隐状态并排画出来。

该图有两个作用：将抽象问题转化为可直接观察的具体实例，并表明研究使用了细粒度数据。

**如果稿件缺少此类示例图，应检查问题描述是否足够具体。**

## 四、Related work

相关工作不应只罗列文献，而应界定方法空间并指出尚未解决的问题。常见的组织方式有两种：

- **按方法族**：邻域方法 → 隐因子模型 → 概率生成模型 → 深度模型，每一族末尾说明为什么不够用
- **按知识基础**：方法论知识基础加理论知识基础，说明两者如何共同推动设计

**强化手段**：在附录中加入对比表，以既有方法为行、以核心挑战或解法目标为列，并标明各方法的覆盖情况。允许一个方法覆盖多列，也允许多个设计共同覆盖一列。该表可以直接回应“本文与方法 X 有何区别”这一常见问题。

**不要贬低基线。**应写“方法 X 在 Y 条件下不适用，因为它假设了 Z”，而不是“方法 X 效果差”。评价应针对假设与适用条件，而非作笼统的优劣判断。

## 五、问题形式化

问题形式化通常包括以下内容，具体配置取决于模型复杂度和目标期刊：

1. **符号表（可选）**。符号较多、跨多个章节使用或容易混淆时设置符号表；符号较少且均能在首次出现处清楚定义时，无须单独列表。
2. **编号的 Definition（可选）**。只有核心对象需要严格区分、定义会被后文反复引用，或形式化边界容易产生歧义时才使用编号定义。一般概念可在正文中直接说明。
3. **问题陈述**：给定什么，输出什么，在什么约束下。
4. **生成过程写成 Algorithm 块**。

**符号不一致是常见且影响较大的问题。**上下标、粗体（向量与矩阵）与斜体（标量）的区分、集合与元素、估计值的帽子记号均须全文统一。符号不一致会削弱稿件的严谨性。中译英时尤其需要检查，因为中文稿常以文字描述替代符号。

## 六、模型章节

先给一张整体框架图，再分模块展开。

每个模块的标准四段式：

1. **这个模块解决什么**：回指引言里的一个或多个挑战或解法目标，保持核心术语一致
2. **为什么不用更简单的做法**：这一项经常被省略，但审稿人通常会关注
3. **形式化**
4. **参数含义与可解释性**：哪些参数可以被赋予业务含义

第 2 点是本体裁可信度的重要来源，通常比增加与设计理由无直接关系的实验更能增强论证。需要回答的问题包括：为什么采用该变体而不是标准结构，为什么采用单变量形式而不是多变量形式，以及为什么在这一层引入该分布假设。每个问题均应以一至两句说明代价与收益。

估计与推断部分应说明目标函数和优化方法。**复杂度分析不是所有稿件的必选项**：当论文声称方法更高效或更具可扩展性、算法复杂度是设计贡献的一部分，或目标期刊特别重视计算性质时，应提供时间或空间复杂度分析。其他情况下，可通过运行时间、计算环境和规模实验说明计算成本，无须为完整形式而强制加入复杂度推导。

## 七、贡献声明：先定位贡献层级，再决定抽象程度

“我们提出了一个新模型”只报告了研究产出，不能单独证明贡献；但经证明具有新颖性和效用的 artifact、算法、模型或方法本身可以构成设计贡献，尤其是在 invention 或研究流的早期阶段。不得规定只有抽象的设计知识才算贡献。

先判断稿件实际支持哪一层贡献：

1. **Artifact contribution**：特定情境中的新 artifact、算法、模型、方法或实现，并有新颖性和效用证据。
2. **Nascent design knowledge**：构念、设计原则、架构、方法或 technological rules，对一类问题具有有限但可说明的迁移性。
3. **Developed design theory**：明确给出目的与范围、构念、设计原则、justificatory knowledge、可检验命题及适用边界。

在证据允许时，最好把具体设计理由提炼为可迁移的设计原则；不得把单一数据集或单次部署的结果直接表述为跨情境规律。

贡献条目数量不必等于挑战、模块或实验数量。一项贡献可以综合多个设计元素；一个设计元素也可能同时支持 artifact、方法论和实践贡献。同一组贡献在引言、讨论和结论中的数量与含义仍须保持一致。

每条贡献应回答：

- 相对于既有知识或 artifact，新增了什么；
- 面向哪一类问题或情境；
- 依靠什么设计或研究活动实现；
- 由什么证据支持；
- 适用边界是什么。

只有“首次将 X 用于 Y”而未说明为何需要适配，“实验结果优于基线”而未说明新增知识，以及超出证据范围的跨情境声称，都不足以形成完整贡献论证。

**Gregor & Hevner (2013) 定位**：invention（新问题新解法）/ improvement（已知问题新解法）/ exaptation（已知解法新领域）/ routine design。明确研究所属位置和知识层级，有助于使评价标准与贡献类型一致；例如，improvement 不需要证明问题本身全新，早期 invention 也不应被强制包装成成熟 design theory。

## 八、可解释性

这是管理类期刊与纯 ML 会议的重要区别。可解释性通常是本领域方法论文的主要贡献或评价维度之一。

规则：**声称可解释就必须展示。**可用的展示手段：

- 可视化学到的参数（各隐状态下的行为分布、状态转移热力图、隐变量漂移矩阵）
- 把隐变量映射到业务概念，并用统计检验说明各状态之间确有差异
- 人工标注或众包验证（例如用 word intrusion 任务检验学到的主题是否连贯）
- 个体层参数直接用于分群，再验证分群结果在外部变量上有差异
- 案例分析：选择若干真实样本，展示模型对他们的分析

只在讨论中声称“我们的模型可解释”而不提供对应证据，容易引发审稿质疑。

## 九、管理启示

必须从模型输出推导，不能是通用建议。

写法三步，缺一不可：

```
模型给出了什么结果 → 这意味着什么 → 因此谁应该在什么时候做什么
```

**有效示例的结构**：模型估计出的个体层参数将用户分为若干群体；进一步分析发现某一群体在时间维度上呈现独特模式；因此，针对该群体的营销活动应安排在特定时段。该结论直接来自模型参数，并体现了相较其他方法的新增信息。

**缺乏研究特异性的示例**：企业应重视用户行为分析；平台应加强个性化推荐。若一项建议不依赖本研究的模型输出，则缺乏研究特异性。

还应主动说明管理启示的适用边界。例如，若数据中没有随机变异，应明确指出研究无法评估用户对推荐的响应性，只验证了表征的预测能力。主动限定推断范围有助于提高稿件的可信度。

## 十、泛化性与局限

这两件事要分开写。

**泛化性**用于回答研究是否仅适用于当前应用。应说明模型的哪些假设具有场景特异性、哪些假设可以跨场景成立；对于场景特定的部分，还应说明迁移时需要修改哪些组件。相关论文通常单设一节，论证模型能否迁移到其他数据类型，并讨论向差异更大的场景迁移时需要调整的层级。

不要只说"本方法具有良好的通用性"。

**局限**应具体到后续研究可以继续处理的问题。每条局限应说明在获得相应数据或条件后如何扩展，而不是仅写“本研究存在不足之处”。常见类型包括：简化了某个建模假设（如个体间独立）、因数据不可得而未纳入某类变量，或尚未在某种极端场景（如极稀疏序列）中验证。

## 十一、评估章节的写作

本节不规定具体评估设计，只说明评估章节的写作要求。

### 常见证据类别

数据描述与描述统计、划分与预处理规则、基线、主结果、统计不确定性、消融、敏感性分析、计算成本、案例、用户研究、形式证明、部署或可视化都可能成为评价证据。先明确论文的核心声称，再选择能够检验该声称的证据；不要先套固定实验清单，再倒推实验支持了什么。

### 描述统计要与引言呼应

描述统计应直接支持引言中对问题特征的判断。每个关键数字都应在正文中承担明确的证据功能。例如，声称数据稀疏时应报告稀疏度分布；声称行为高度变异时应报告方差；声称多数用户轨迹较短时应报告活跃期的中位数。

### 基线呈现

按族列举，每族说明代表什么范式（静态 / 动态 / 深度，或经典统计模型 / 神经模型）。

必须说明：**为保证公平比较，对基线进行了哪些调整**。例如，向各基线提供相同信息、统一训练与测试单元，或将基线中的相应组件替换为相同版本。缺少这些说明会使读者无法判断比较是否公平。

超参调优要说明：调了哪些、搜索范围、在哪个集合上选。

### 评价证据与消融

- 对性能、准确性、效率或满足需求等 criterion claims，使用与目标一致的基准、指标、复杂度、运行时间或用户任务评价。
- 对“某机制导致某结果”等 causal or mechanism claims，使用能够识别该机制的实验、识别设计或机制检验；消融本身通常不足以证明因果机制。
- 对跨数据、组织或情境的 context claims，使用跨情境验证、自然环境部署、稳健性分析或明确的边界证据。

消融适用于可合理拆分的计算设计，以及“某组件带来增量作用”的声称。每组消融应说明移除了什么、改变了什么声称相关指标，以及结果支持或不支持什么结论。若组件相互依赖、无法独立移除，或主要服务于可解释性、约束满足、安全性或可用性，应采用结构化变体、敏感性分析、形式证明、案例、用户研究或其他更合适的评价。

如果移除某个组件后相关指标几乎不变，应如实报告，并重新判断它是否服务于另一项声称或是否有保留必要。不得因为有 N 个设计元素就机械要求 N 组消融，也不得仅按影响大小排序便声称得到了可迁移的设计知识。

### 结果的语言

- **区分相对值与百分点**。"提升 7%"必须说明是相对提升还是绝对百分点差，并在表注写明计算方式。
- **显著性检验应明确检验对象**：说明是对交叉验证各折进行配对检验，还是对多组随机初始化结果进行秩和检验。
- **在证据支持且任务允许实质性修改时解释性能差异**，并指向相应设计决策。润色模式只澄清原文已有解释；若解释缺失，应提示作者补充，不得根据性能差异或消融结果自行编造机制。
- **解释反常结果**。如果某个基线在特定设置下表现更好，应说明可能原因。忽略此类结果会削弱报告的完整性。

### 表格规范

加粗最优值并在表注说明含义。表注必须包含：指标定义或公式编号、数值是否做过缩放、报告的是训练集还是测试集、超参在哪个集合上调的、显著性标记的含义。多指标时列顺序全文一致；评价证据应能追溯到相应设计决策或声称，但不要求所有模型小节都有消融行。

### 性能声称的强度

强度阶梯与缓冲语的完整版本在 `cn-en-transfer.md` 第三节，写结果段落之前先看那里。评估章节特有的三条补充：

- 不显著的改进不要写成 slightly better，直接说差异不显著。
- 计算效率的声称需要数字支持。仅写 our model is efficient 而不报告运行时间或复杂度，不能形成可核查的证据。
- 如果表中加粗的最优值相较其他结果并不具有统计显著性，应在表注中说明。加粗会被读者理解为结果判断的一部分。

## 十二、常见拒稿原因清单

结构诊断时按这个表逐条过：

| 问题 | 表现 |
|---|---|
| 挑战缺乏依据 | 列出的困难可由既有方法处理，或对结果无实质影响 |
| 设计与挑战脱节 | 模型包含复杂组件，但这些组件与声称要解决的问题无关 |
| 理论定位不实 | 声称 theory-guided 或理论贡献，但理论未产生设计含义；或在没有相关理论时强贴标签 |
| 评估不支持声称 | 声称模型可解释但未提供展示；声称模型高效但未报告复杂度或运行时间 |
| 基线过时或调参不足 | 仅与较早的方法比较，或未说明基线的调参方式 |
| 评价与声称不对应 | 声称组件有增量作用却无适合的消融或替代证据，或对不可拆分设计机械要求消融 |
| 贡献声明与实际不符 | 引言承诺三条，讨论只兑现一条 |
| 管理启示空洞 | 通用建议，换一篇论文也成立 |
| 单数据集且未讨论泛化 | 被判定为一个应用而非方法贡献 |

## 十三、摘要与标题

摘要影响稿件能否进入进一步评审，标题影响读者是否继续阅读。两者都容易受到中文写作习惯的影响。

### 摘要的五个部分

按顺序，通常 150–250 词，具体长度看期刊：

1. **现象与业务张力**（1–2 句）。给规模或给矛盾，不写背景介绍。
2. **既有方法为什么不够**（1 句）。点到方法族层面，不是"研究尚存不足"。
3. **提出什么，关键设计是什么**（2–3 句）。摘要应明确呈现关键设计。只写“我们提出了一个新框架”无法完成说明设计内容的功能。
4. **数据与结果**（1–2 句）。概括数据来源、评估范围和主要结果，原则上避免罗列具体性能数值。优先说明结果的方向、稳定性和适用条件；只有目标期刊明确要求、某个数字对理解贡献不可替代，或用户明确要求时才保留关键数字。摘要中出现的数字必须与正文完全一致。
5. **贡献或启示**（1 句）。与正文的贡献层级一致，说明新增 artifact、初步设计知识或理论贡献，而不是只写“具有重要意义”。

### 摘要的常见毛病

- **路线图式写法**。"本文首先……然后……最后……"是中文摘要的习惯。英文摘要不写目录，写结论。
- **缩写未定义**。摘要会被单独阅读（检索结果页、会议手册），所以缩写在摘要里定义一次，正文里再定义一次。
- **不必要地罗列具体数字**。摘要应突出研究问题、关键设计和主要结论，不应压缩成结果表的复述。确需保留的关键数字必须与正文一致。
- **只有方法没有结果，或只有结果没有设计**。
- **动词用过去时**。摘要同样统一用现在时。

### 标题

标题要同时含**方法**和**问题**两端。只有方法端，读者不知道用在哪；只有问题端，读者看不出贡献是在方法上。

- 避免 `Research on...` / `A Study of...` / `Analysis of...`。这是“……研究”的直译，在英文期刊标题中不常见，也不能说明具体问题或方法。
- 避免用 `Novel` / `New` / `Improved` 开头。新颖性需要由具体设计体现，不能仅由标题中的形容词声明。
- 避免只给方法名或只给缩写。
- 冒号结构在本领域常见：冒号前给机制或方法，冒号后给场景或问题。
- 不用未定义的缩写，除非是本领域公认的（MCMC、LSTM 一类）。
- 作者自造的方法名可以进标题，前提是它提示了核心机制，而不只是一串首字母。

判断方法：让同领域但不研究该具体主题的读者阅读标题，并确认其能否识别研究问题和大致方法。若无法识别，标题提供的信息仍不充分。
