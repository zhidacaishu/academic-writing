# 设计科学论文体裁规范（IS 与定量营销的方法类论文）

适用期刊：Information Systems Research、MIS Quarterly、Management Science、Marketing Science、INFORMS Journal on Computing、JMIS、Decision Support Systems、POM。

国内《管理科学学报》《系统工程理论与实践》的方法类投稿也适用本文件的**结构**规范（挑战架构、设计与评估的对应、贡献声明的形状），这套骨架是跨语言的。但**文体**规范不适用：中文学术写作有自己的语域和句法习惯，不要拿英文期刊的句长、人称、时态标准去改中文稿。参见 `cn-en-transfer.md` 第五节。

这类论文的货币是"问题 → 设计 → 评估"三者的闭合。审稿人反复问的就是三个问题：

1. 这个问题真的存在、真的重要吗，还是你自己造出来的？
2. 你的设计是针对这个问题的，还是只是换了个更复杂的模型？
3. 评估证明的是你声称的那件事吗？

下面所有规范都服务于让这三个问题有明确答案。

## 一、挑战架构：本体裁最核心的结构装置

这个骨架在本领域的高水平论文里高度稳定：

```
引言列举 N 个挑战或问题特征（通常 3 个）
        ↓ 一一对应
模型的 N 个设计决策
        ↓ 一一对应
贡献声明的 N 条
        ↓ 一一对应
消融实验的 N 组
```

四条线必须编号一致、顺序一致、措辞一致。这是审稿人最容易检查、也最容易发现断裂的地方，是结构诊断的第一必查项。

常见的挑战类型（供对照，不是模板）：

- 数据层面：稀疏、高维、非平稳、异质
- 行为层面：多面性与并发、动态交互、外部事件影响
- 方法层面：既有模型的假设过强、参数量随组合爆炸、隐变量不可识别
- 可用性层面：黑箱模型无法支撑管理决策

### 挑战怎么写

- 一个挑战一段，段首直接命名，段尾用一句收束成可操作的技术问题（"因此，挑战在于如何……"）。
- 挑战必须在**方法层面**成立，不是应用层面。"电商数据规模大"不是挑战；"多变量点过程一次只允许一种行为发生，无法直接建模并发行为，且枚举所有行为组合会导致参数量指数爆炸"才是挑战。
- 证据要点名到方法族：哪一类方法、因为什么假设、所以做不到什么。只写"现有研究存在不足"等于没写。
- 数量控制在 2 到 4 个。超过四个说明没提炼，读者记不住，后面的对应关系也维持不住。

## 二、Kernel theory：与纯 ML 论文的分界线

ISR 与 MISQ 要求 justificatory knowledge：模型结构必须有理论依据，不能只说"这样效果好"。这是设计科学论文投管理类期刊与投 KDD/WWW 的根本差别，也是中国作者最常踩空的地方。

理论正确嵌入的标志是它**产出了具体的模型约束**。本领域的高水平论文里，理论通常决定三类东西：

1. **隐变量的语义**。隐状态不是无名的 K 个类别，而是对应理论中的某个阶段、状态或倾向。
2. **参数约束**。理论若预言某个量随阶段单调变化，模型就应把这个单调性写成约束，并用它来识别隐状态的顺序。
3. **变量选择的依据**。为什么用这两个协变量而不是另外两个，答案来自理论对机制的划分，而不是数据可得性。

有的论文还会额外做一个小型行为实验，验证理论假定的因果前提在本场景成立。这不是必需的，但能显著提高理论部分的可信度。

**检验方法**：把模型章节的每个设计决策列成清单，逐条问"这一条对应理论里的哪句话"。答不上来的就是装饰性引用，审稿人会发现。反过来也成立。理论预言的性质如果模型没实现，要解释为什么不实现。

**典型失误**：把理论写成一节独立的文献综述，之后再不提。正确做法是理论章节结尾直接落到对模型的设计含义上，形成"因为理论说 A，所以模型必须有 B"的显式链条。

## 三、引言里的示例图

本领域的方法论文通常在引言或紧随其后放一张具体示例图：一条真实的用户旅程、一段真实的行为序列，把可见的行为与不可见的隐状态并排画出来。

作用有两个：把抽象问题变成读者能盯着看的东西，同时顺带说明作者确实有细粒度数据。

**如果你的论文没有这张图，通常说明问题还没讲具体。**图要用真实数据画，不要用示意性方框。标注要能对上论文后面用的符号。

## 四、Related work

不是罗列，是画出方法空间并指出空位。两种常见组织方式：

- **按方法族**：邻域方法 → 隐因子模型 → 概率生成模型 → 深度模型，每一族末尾说明为什么不够用
- **按知识基础**：方法论知识基础加理论知识基础，说明两者如何共同推动设计

**强化手段**：附录放一张对比表，行是既有方法，列是你列举的那 N 个挑战，格子打勾。这张表能挡掉大量"你和 X 有什么区别"的审稿意见，性价比极高。

**不要贬低基线。**写"方法 X 在 Y 条件下不适用，因为它假设了 Z"，不写"方法 X 效果差"。审稿人可能就是 X 的作者。

## 五、问题形式化

标准配置四件套：

1. **符号表**。首次出现的每个符号都要在表里。
2. **编号的 Definition**。把问题涉及的每个核心对象单独定义，每个 Definition 之后给一句直觉解释，别让读者只面对形式化。
3. **问题陈述**：给定什么，输出什么，在什么约束下。
4. **生成过程写成 Algorithm 块**。

**符号一致性是硬伤重灾区。**上下标、粗体（向量与矩阵）与斜体（标量）的区分、集合与元素、估计值的帽子记号，全文必须统一。审稿人发现符号不一致会连带质疑整篇的严谨性。中译英时尤其容易出错，因为中文稿常用文字描述代替符号。

**判断形式化是否充分的标准**：读者能否照着生成过程仿真出数据。写不出来说明模型没定义清楚。有的论文会真的用自己的生成过程仿真数据、再反估参数来验证估计程序的准确性，这个做法很加分。

## 六、模型章节

先给一张整体框架图，再分模块展开。

每个模块的标准四段式：

1. **这个模块解决什么**：回指引言里的某个挑战，用同样的措辞
2. **为什么不用更简单的做法**：最常被省略，但审稿人一定会问
3. **形式化**
4. **参数含义与可解释性**：哪些参数可以被赋予业务含义

第 2 点是本体裁可信度的主要来源，比多跑一个实验有用。典型的需要回答的问题：为什么用这个变体而不是标准结构、为什么用单变量形式而不是多变量、为什么在这一层引入这个分布假设。每个都用一两句说清代价与收益。

估计与推断部分要给：目标函数、优化方法、**复杂度分析**。复杂度分析常被中国作者省略，但 IJOC 和 ISR 会要。

## 七、贡献声明

不能写的三种：

- "我们提出了一个新模型"：新本身不构成贡献
- "我们首次将 X 应用于 Y"：除非能说明 Y 的什么特性使得 X 必须被改造
- "实验证明我们的方法优于基线"：这是结果，不是贡献

要写的是**设计知识**：什么样的问题特征，应当用什么样的设计应对，为什么，代价是什么。

可用句式：

```
We show that [问题特征] can be addressed by [设计原则],
which [带来什么] without [付出什么代价].
```

判断标准：这条贡献能不能被别人拿去用在另一个场景。"我们做了个注意力点过程"不能；"用单变量点过程配合定制的 hurdle 模型，可以在不引起参数指数爆炸的前提下同时建模行为并发性与消费量"能，因为它可以迁移到任何存在并发行为的场景。

三类贡献分开写，别混在一段：

1. **方法论贡献**（设计知识，可迁移）
2. **应用贡献**（对这个业务问题的新理解）
3. **管理启示**（见第九节）

**Gregor & Hevner (2013) 四象限定位**：invention（新问题新解法）/ improvement（已知问题新解法）/ exaptation（已知解法新领域）/ routine design。写清楚自己在哪个象限，可以避免审稿人用错误的标准衡量你。比如你做的是 improvement，却被要求证明问题是全新的。

## 八、可解释性

这是管理类期刊与纯 ML 会议的关键差别。本领域的方法论文几乎都把可解释性作为卖点。

规则：**声称可解释就必须展示。**可用的展示手段：

- 可视化学到的参数（各隐状态下的行为分布、状态转移热力图、隐变量漂移矩阵）
- 把隐变量映射到业务概念，并用统计检验说明各状态之间确有差异
- 人工标注或众包验证（例如用 word intrusion 任务检验学到的主题是否连贯）
- 个体层参数直接用于分群，再验证分群结果在外部变量上有差异
- 案例分析：挑几个真实样本走一遍模型的推断过程

只在讨论里说一句"我们的模型可解释"而没有对应证据，是常见的审稿意见来源。如果你的模型比基线更黑，需要额外理由说明为什么值得。

## 九、管理启示

必须从模型输出推导，不能是通用建议。

写法三步，缺一不可：

```
模型给出了什么结果 → 这意味着什么 → 因此谁应该在什么时候做什么
```

**好的例子的形状**：模型估计出的个体层参数把用户分成若干群；进一步分析发现某一群在时间维度上有独特模式；因此针对该群体的营销窗口应放在特定时段。结论直接来自模型参数，别的方法给不出来。

**坏的例子**：企业应重视用户行为分析；平台应加强个性化推荐。换一篇论文也成立的建议就是空的。

另外一个值得学的诚实做法：主动写出启示的边界。例如明确说明数据中没有随机变异，因此无法评估用户对推荐的响应性，论文只验证了表征的预测能力。**主动标注边界比等审稿人指出要好**，而且会提高整篇的可信度。

## 十、泛化性与局限

这两件事要分开写。

**泛化性**回答"这是不是只是一个应用"。写法：说明模型的哪些假设是场景特定的、哪些不是；对于场景特定的部分，说明换场景时要改什么。高水平论文通常会单设一节，论证模型没有对当前场景做特殊假设，因此可迁移到其他数据类型，并进一步讨论迁移到更远的场景（例如从文本到图像）需要改动哪一层。

不要只说"本方法具有良好的通用性"。

**局限**要具体到后续研究可以接手。每条局限附带"如果有数据该怎么扩展"，比"本研究存在不足之处"有用得多。常见的三类：某个建模假设被简化了（如个体间独立）、某类变量因数据不可得未纳入、未在某种极端场景（如极稀疏序列）验证。

## 十一、评估章节的写作

评估怎么做是作者的事。这里只讲**怎么写**。

### 标准套件

数据描述与描述统计表、划分与预处理规则、基线（按族组织）、主结果表与显著性检验、消融、敏感性分析、计算成本、案例分析或可视化。不必全有，但缺哪一项要有理由。

### 描述统计要与引言呼应

描述统计不是走过场。每个引人注目的数字都要在正文里被用到一次，用来支撑你在引言里对问题特征的断言。声称数据稀疏就报稀疏度分布；声称行为高度变异就报方差；声称多数用户轨迹很短就报活跃期的中位数。

### 基线呈现

按族列举，每族说明代表什么范式（静态 / 动态 / 深度，或经典统计模型 / 神经模型）。

加一个**业务基线**（公司当前实际在用的做法）比只跟学术方法比更有说服力，也直接支撑管理启示。

必写的一句：**为公平比较对基线做了什么调整**。例如把同样的信息注入各基线、统一训练与测试单元、把基线中的组件替换成与自己相同的版本。缺这一句，审稿人会怀疑基线被故意削弱。

超参调优要说明：调了哪些、搜索范围、在哪个集合上选。

### 消融的写法

每组三句：关掉了什么 / 掉了多少 / 说明了什么。

**反面写法**：把消融堆成一张表，然后说"各组件均有贡献"。要进一步指出哪个组件贡献最大、是否符合设计预期。这个排序本身就是设计知识。

如果某个组件消融后性能几乎不变，不要藏。要么承认它主要服务于可解释性而非精度，要么考虑砍掉它。审稿人会自己算。

### 结果的语言

- **区分相对值与百分点**。"提升 7%"必须说明是相对提升还是绝对百分点差，并在表注写明计算方式。
- **显著性检验要写清检验对象**：是对交叉验证各折的配对检验，还是对多组随机初始化的秩和检验。
- **解释为什么赢，不只报告赢了**。在结果段落里给机制解释，指回你的某个设计决策。
- **也要解释反常结果**。某个基线在特定设置下反超，要说明原因。装看不见比承认更糟。

### 表格规范

加粗最优值并在表注说明含义。表注必须包含：指标定义或公式编号、数值是否做过缩放、报告的是训练集还是测试集、超参在哪个集合上调的、显著性标记的含义。多指标时列顺序全文一致；消融表的行标签要对得上模型章节的小节号。

### 性能声称的强度

强度阶梯与缓冲语的完整版本在 `cn-en-transfer.md` 第三节，写结果段落之前先看那里。评估章节特有的三条补充：

- 不显著的改进不要写成 slightly better，直接说差异不显著。
- 计算效率的声称要有数字。写 our model is efficient 而没有运行时间或复杂度分析，等于没写。
- 表里加粗的最优值，如果领先幅度在检验下并不显著，表注要说明。加粗本身就是一种声称，读者会当成结论看。

## 十二、常见拒稿原因清单

结构诊断时按这个表逐条过：

| 问题 | 表现 |
|---|---|
| 挑战是编的 | 列出的困难其实既有方法能处理，或对结果无实质影响 |
| 设计与挑战脱节 | 模型很复杂，但复杂的部分和声称要解决的问题无关 |
| 理论装饰化 | 理论只在引言点名，模型结构与它无关 |
| 评估不支持声称 | 说可解释但没展示；说高效但没报复杂度或运行时间 |
| 基线过时或调参不足 | 与五年前的方法比赢了不算赢；没说明基线怎么调的 |
| 消融缺失或不对应 | 无法判断性能来自哪个组件 |
| 贡献声明与实际不符 | 引言承诺三条，讨论只兑现一条 |
| 管理启示空洞 | 通用建议，换一篇论文也成立 |
| 单数据集且未讨论泛化 | 被判定为一个应用而非方法贡献 |

## 十三、摘要与标题

摘要决定稿子会不会被送审，标题决定会不会被点开。两者都被中文习惯影响得很深。

### 摘要的五个部分

按顺序，通常 150–250 词，具体长度看期刊：

1. **现象与业务张力**（1–2 句）。给规模或给矛盾，不写背景介绍。
2. **既有方法为什么不够**（1 句）。点到方法族层面，不是"研究尚存不足"。
3. **提出什么，关键设计是什么**（2–3 句）。必须让审稿人在摘要里就看见设计。只写"我们提出了一个新框架"等于放弃这三句。
4. **数据与结果**（1–2 句）。带具体数字，且与正文表格完全一致。
5. **贡献或启示**（1 句）。是设计知识，不是"具有重要意义"。

### 摘要的常见毛病

- **路线图式写法**。"本文首先……然后……最后……"是中文摘要的习惯。英文摘要不写目录，写结论。
- **缩写未定义**。摘要会被单独阅读（检索结果页、会议手册），所以缩写在摘要里定义一次，正文里再定义一次。
- **数字与正文对不上**。改稿时最容易漏掉摘要，交付前专门核一遍。
- **只有方法没有结果，或只有结果没有设计**。
- **动词用过去时**。摘要同样默认现在时。

### 标题

标题要同时含**方法**和**问题**两端。只有方法端，读者不知道用在哪；只有问题端，读者看不出贡献是在方法上。

- 避免 `Research on...` / `A Study of...` / `Analysis of...`。这是"……研究"的直译，英文期刊里几乎不出现，也不传递任何信息。
- 避免用 `Novel` / `New` / `Improved` 开头。新本身不是卖点。
- 避免只给方法名或只给缩写。
- 冒号结构在本领域常见：冒号前给机制或方法，冒号后给场景或问题。
- 不用未定义的缩写，除非是本领域公认的（MCMC、LSTM 一类）。
- 作者自造的方法名可以进标题，前提是它提示了核心机制，而不只是一串首字母。

判断方法：把标题念给一个同领域但不做这个题的人听，他能不能说出这篇解决什么问题、大概怎么解决。说不出来就还没写好。
